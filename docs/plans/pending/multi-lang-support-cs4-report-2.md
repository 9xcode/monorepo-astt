# Complete i18n Implementation Plan for Your Astro + Svelte Project

## Critical findings first (what previous research got wrong)

Before the plan: three important corrections to your research documents.

**`astro-i18next` is dead.** The OAI report 1 recommended it as the winner. It is archived, unmaintained, and confirmed incompatible with Astro 5. Do not use it. This was the biggest error in the provided research.

**i18next itself is incompatible with Astro 5** at this time. Multiple Astro 5 developers and the Phrase engineering team confirmed this in early 2025 guides. This eliminates the CS4 report 1's "Strategy C" which used `@astrojs/i18next`.

**Paraglide v2's Vite plugin requires SSR.** The current `@inlang/paraglide-js` (v2) documentation shows `output: "server"` in all Astro examples. For your 100% static site, you use the older but maintained Astro-specific integration: `@inlang/paraglide-astro`. It detects locale by reading the `lang` attribute on `<html>`, which works perfectly with SSG and Svelte islands.

## Part 5: Svelte Widgets — Zero Runtime i18n

This is the key architectural decision. Your Svelte widgets receive translated strings as **props from Astro**. No i18n library runs in the browser whatsoever.

```astro
---
// pages/tools/[tool].astro (English)
import MortgageWidget from '@/features/mortgage-calculator/Widget.svelte';
import * as m from '../paraglide/messages.js';
---

<MortgageWidget
  client:load
  labels={{
    calculate: m.tool_calculate(),
    reset: m.tool_reset(),
    result: m.tool_result(),
  }}
/>
```

```svelte
<!-- features/mortgage-calculator/Widget.svelte -->
<script lang="ts">
  interface Labels {
    calculate: string;
    reset: string;
    result: string;
  }
  let { labels }: { labels: Labels } = $props();
</script>

<button>{labels.calculate}</button>
```

The `m.tool_calculate()` call happens at build time in Astro's server context. By the time the HTML file ships to the CDN, it already contains the correct German or English string. The Svelte bundle receives a plain string — no i18n runtime, zero bytes.

## Part 7: URL Slug Translation (SEO bonus — for German)

You asked about translated URLs. For example: `/tools/mortgage-calculator` in English and `/de/tools/hypothekenrechner` in German (not just `/de/tools/mortgage-calculator`).

This is optional but great for German SEO. Here's how to implement it cleanly:

```ts
// src/i18n/slugMaps.ts
// Left side = canonical English slug, Right side = locale slug
export const toolSlugMap: Record<string, Partial<Record<'de', string>>> = {
  'mortgage-calculator':           { de: 'hypothekenrechner' },
  'compound-interest-calculator':  { de: 'zinseszinsrechner' },
  'budget-planner':                { de: 'haushaltsplaner' },
  'loan-amortization-calculator':  { de: 'darlehenstilgungsrechner' },
  // ... add for each tool as you translate
};

export function getLocalizedSlug(englishSlug: string, locale: string): string {
  if (locale === 'en') return englishSlug;
  return toolSlugMap[englishSlug]?.[locale as 'de'] ?? englishSlug;
}

export function getEnglishSlug(localizedSlug: string, locale: string): string {
  if (locale === 'en') return localizedSlug;
  const entry = Object.entries(toolSlugMap).find(
    ([, v]) => v[locale as 'de'] === localizedSlug
  );
  return entry?.[0] ?? localizedSlug;
}
```

Then in `pages/de/tools/[tool].astro`:
```ts
export async function getStaticPaths() {
  const enTools = await getCollection('tools-en');
  return enTools.map(tool => ({
    params: { tool: getLocalizedSlug(tool.slug, 'de') }, // ← German URL slug
    props: { entry: tool, lang: 'de' as const, canonicalSlug: tool.slug },
  }));
}
```

The language switcher then uses `getEnglishSlug()` to find the cross-locale equivalent when switching between `/de/tools/hypothekenrechner` and `/tools/mortgage-calculator`.
